# kOS X-Desktop (`xdesktop`) — Implementation Plan

## 1. Goal

Render GUI Linux applications (Firefox, terminals, editors…) running in Kubernetes pods
**inside the KuberneticOS web desktop**, using a **central shared X server pod** — the
network-transparent X11 model (apps are "X clients", we host the X server) — plus a
**Terminal** window app for shell access.

Confirmed decisions (from research/discussion):

- **Central shared xserver pod** (`kos-xserver`), not per-session sidecars. App pods stay
  stock: only need `DISPLAY` env + an xauth cookie.
- **One virtual display per kOS window** (Xvfb `:21`, `:22`, …) → one kOS window per app =
  the SSH-X11 per-window feel.
- **Capture stack = x11vnc (RFB)** for v1; client-side canvas via `@novnc/novnc`.
  KasmVNC/Selkies (H.264/WebRTC) are later quality upgrades, not v1.
- **Terminal = `kubectl exec`** via `client-go` `remotecommand` (WS v5 + SPDY fallback) —
  no pod requirements beyond a shell.
- Single-user kOS instance (one kubeconfig) — no multi-user auth layer yet.

## 2. Architecture

```
┌─ app pod (shipped image) ───────────┐      ┌─ kos-xserver pod (StatefulSet) ──────────┐
│ firefox, gimp, vscode …             │      │  Xvfb :21 :22 :23 …  (/tmp/.X11-unix)     │
│ DISPLAY=kos-xserver.kos-xserver:21 ─┼─X11─▶│  xauth cookie per display (Secret)        │
│ XAUTHORITY=/kos-xauth/cookie        │      │  x11vnc 5921 5922 …  (bind 0.0.0.0)       │
│ (X11 client libs; nothing else!)    │      │  openbox/WM per display (decorations)     │
└─────────────────────────────────────┘      │  supervisord-style per-display supervisor │
                                             └───────────────┬───────────────────────────┘
┌─ kos-server (Go, existing) ─────────────────────────────────┼───────────────────────────┐
│  POST /api/xdisplay  → allocate display N, gen cookie,      │                           │
│                        patch app pod env/secret (or exec)    │  net.Dial podIP:5900+N    │
│  GET  /api/xdisplay/ws?token=…  (WS upgrade = websockify) ◀──┴── gorilla websocket ⇄ TCP │
│  GET  /api/exec/ws?cluster&namespace&pod&container → remotecommand exec stream (terminal)  │
└────────────────────────────────────────────────────────────────────────────────────────────┘
                  ▲ WebSocket (RFB binary frames / xterm text+JSON control)
        ┌─ kOS web desktop ────────────────────────────────────────────┐
        │ RemoteWindow window-app (noVNC canvas inside kos Window)      │
        │ Terminal window-app (xterm.js + fit/attach)                   │
        │ Cluster Explorer: "Open App…" / "Open Terminal" on pods       │
        └───────────────────────────────────────────────────────────────┘
```

**Numbers/ports**: Xvfb displays 21–79 (max 59 concurrent displays/window; configurable),
x11vnc on `5900+N`, kos-xserver Service exposes `6000–6079` (X11 TCP) + `5921–5979`
(optional direct VNC for debugging). Only the `DISPLAY` port range needs Service exposure
for app pods.

**Auth for X11-over-TCP**: per-display xauth cookie (16-byte random hex), generated by
kos-server, stored as a k8s Secret mounted into the app pod at `/kos-xauth`, `XAUTHORITY`
env injected. Never `xhost +`. Short-lived on release.

**shm**: xserver pod gets `emptyDir{medium:Memory}` `/dev/shm` sized ≥1Gi (Firefox
rendering).

**Kubernetes resources (new manifest dir `deploy/`)**:

- `deploy/kos-xserver.yaml` — StatefulSet (ordered, stable identity), image built from
  `deploy/xserver/Dockerfile` (Debian slim + `xvfb`, `x11vnc`, `xauth`, `openbox` or
  minimal WM, fonts-noto, supervisord); resources ~ requests 250m/512Mi, limits 2/4Gi;
  shm 1Gi.
- Service `kos-xserver` exposing 6000–6079 (X11) + 5921–5979 (optional VNC debugging).
- RBAC additions for kos-server SA: `get/list/watch pods`, `create/get/delete secrets` in
  the kos namespace, `pods/exec` (create), optional `deployments/patch` (managed mode,
  M2+).

## 3. Server changes (`server/`)

New file `server/xdisplay.go` + `server/exec.go`, wiring in `main.go`.

### 3.1 Display allocator

- In-memory registry `map[int]DisplaySession{CookieHash, PodTarget, AppName, CreatedAt}`
  guarded by mutex; survives only server lifetime (display is stateless to recreate).
- `POST /api/xdisplay` body `{cluster, namespace, pod, container, app, command[]}` →
  1. pick free display N (static pool, `KOS_XDISPLAY_POOL`, default 5 → 21–25);
  2. generate xauth cookie; run `xauth add <display>: MIT-COOKIE-1 <cookie>` inside the
     xserver pod (exec) so Xvfb trusts the client;
  3. exec into the app pod to launch the command with
     `DISPLAY=kos-xserver.<kos-namespace>:<N>` and an `XAUTHORITY` cookie delivered
     through the exec stream (cookie written via stdin-piped `xauth`);
  4. record session; returns `{display, token, wsPath}` where `token` is a one-use,
     TTL'd bearer to open the WS stream.
- `DELETE /api/xdisplay?token=` — kills the launched process (exec `kill` on the session
  leader PID recorded at launch), waits, frees the display.
- `GET /api/xdisplay/list` — active displays (for reconnect after browser reload).

### 3.2 WS stream proxy (websockify clone)

- `GET /api/xdisplay/ws?token=…` — gorilla `websocket` upgrade, then
  `net.Dial("tcp", xserverServiceIP:5900+N)`, two goroutines doing binary-frame ⇄ TCP
  copy (the `novnc/websockify-other/golang` reference pattern). Binary-only frames;
  ping/pong 10s; streams get a long idle timeout (e.g. 5 min, activity-reset), not the
  15s request budget.
- Token → display mapping validated per upgrade; cookie + pod handle never leave the
  server.

### 3.3 Terminal exec bridge (`server/exec.go`)

- `GET /api/exec/ws?cluster&namespace&pod&container` — upgrade, then
  `remotecommand.NewFallbackExecutor(NewWebSocketExecutor, NewSPDYExecutor, fallback)`
  with `StreamOptions{Stdin: session, Stdout: session, Stderr: session, Tty: true,
  TerminalSizeQueue: session}` (periscope/agenttier pattern: session implements
  io.Reader/Writer; resize via text-JSON control frames, binary = data).

Protocol (browser ↔ server WS):

| Frame | Meaning |
|---|---|
| binary | raw stdin/stdout data (stdout+stderr merged server-side on TTY) |
| text `{"type":"resize","cols":80,"rows":24}` | terminal resize |
| text `{"type":"error","message":"…"}` / `{"type":"closed"}` | terminal lifecycle |

- Shell pick: `exec /bin/bash 2>/dev/null || exec /bin/sh` fallback chain.

### 3.4 X-server pod health

- `GET /api/xdisplay/health` — TCP dials the x11vnc range on the xserver pod + pod
  existence; offline mode returns `available:false` (matches the existing offline
  philosophy: never 500).

## 4. Frontend changes

### 4.1 New cluster transport module `src/cluster/streams.ts`

- `openXDisplaySession(params): Promise<{token, display}>` (calls `/api/xdisplay` with
  the same fetch discipline — this file is the **only** place WS/streams live; preserves
  rule 1, `fetch` stays confined to `client.ts`/`streams.ts`).
- `connectRfbStream(wsPath, token, opts)` — thin wrapper around `@novnc/novnc` `RFB`
  (npm `@novnc/novnc`), returns handle with `disconnect()`.
- `connectExecStream(wsPath, params, handlers)` — Binary/text frame protocol per §3.3.

### 4.2 Window apps

- **`src/window-apps/XDesktop.tsx` (+ `xdesktop.css`)**:
  - Props: `{cluster, namespace, pod, container, app?, command?, title}`.
  - Mount → `openXDisplaySession` → RFB connect → canvas fills window client area.
  - Lifecycle: minimize keeps the session; close → `DELETE /api/xdisplay`; tab
    close kills; window blur keeps the session (background framerate fine).
  - Clipboard: text-only via noVNC clipboard sync.
- **`src/window-apps/Terminal.tsx` (+ `terminal.css`)**: xterm.js (`@xterm/xterm`,
  `@xterm/addon-fit`, lazy-imported chunk); props `{cluster, namespace, pod, container?}`;
  title `Terminal — <pod>`.
- **`src/window-apps/registry.ts`**: register `Terminal` and `XDesktop` as production
  apps.
- **Cluster Explorer integration**: pod rows get "Open terminal" and (annotation-gated:
  `kos.dev/x-app: "<command>"`) an "Open GUI" action that dispatches `ADD_WINDOW` with
  matching props.
- **Start Menu / desktop context menu**: quick-launch `Terminal (pod picker)` and
  `App session…` entries.

### 4.3 State

- No new reducer actions needed: sessions ride `Window.props` + existing window
  lifecycle. Only addition: verify whether `WindowManager` unmounts minimized windows —
  if so, add a `keepAlive` flag on app definitions (small reducer/type change).
- Event bus (`src/state/events.ts`): `xsession:closed` / `exec:closed` events so Cluster
  Explorer can refresh badges.

## 6. Open sub-decisions (resolved defaults)

1. **How the app pod gets `DISPLAY`/cookie for existing pods**: (a) exec-launch env
   injection only — works always, app dies with exec session — **default (v1)**;
   (b) Secret + user-added mount for persistent sessions — doc-only in v1.
2. **Deployment patching (managed mode)** — v1 does *not* create Deployments; app
   sessions require an existing pod. M2+.
3. **Static display pool size** — default **5 displays** (21–25), env
   `KOS_XDISPLAY_POOL`.

## 8. Risks / notes

- X11-over-TCP inside the cluster is plaintext — acceptable single-user dev posture;
  document it; the browser leg is always TLS/WSS via kos-server.
- Chromium sandbox may need `seccompProfile: Unconfined` per pod — document, don't
  enforce.
- gorilla/websocket vs alternatives: gorilla is de-facto standard; fine.
- VERIFY during M3: does `WindowManager` unmount minimized windows (stream keep-alive).
